# @harrhy/auth

Jack Auth's browser sign-in, consent, app directory, access management, enrollment, and support-login UI. ZITADEL remains the separate issuer and owns identities, passwords, sessions, grants, and token exchange. This app calls supported native APIs and stores only its own access ledger, Radio enrollment history, appearance choices, and short-lived browser state. It does not import `@harrhy/identity` as a privileged provider client.

`src/server.mjs` is the Node 26 entry point. Sign-in, delegated consent, account, email recovery, enrollment, device approval, the app directory, sessions, access management, People, groups, and service inventory use Remix components with one shared document shell in `src/document.tsx`. The Node entry uses Remix’s Web request listener and routers. Browser controller decisions still live in `src/server.mjs`, `src/access-routes.mjs`, and `src/support-routes.mjs` while they are separated by route. `config/applications.json` and `config/services.json` hold the app's reviewed client and directory policy. An application's optional `allowedUserIds` restricts direct and delegated authorization to those exact native user IDs in addition to its existing role/grant checks; an empty list denies everyone. TeaCMS stays held with an empty source list. Its initial release requires the checked policy-enforcing image and a private owner-only runtime list, not a project-wide hold removal. Runtime registry overlays, including Ref preview entries, must be preserved by the deployment operator. `integrations/` contains the native action source retained with its separate license. `__tests__/` holds the app's server and browser fixtures. The [architecture](../../docs/auth/architecture.md), [support-login contract](../../docs/auth/support-login.md), [product decisions](../../docs/auth/product.md), and [design guide](../../docs/auth/design.md) provide details.

## Run and check

From the Harrhy root, run `npm ci`, then `npm run check --workspace @harrhy/auth`. The check typechecks the Remix components and native provisioning effect path (including compile-negative service/state contracts), runs the Node contract tests, and exercises the actual HTTP routes in Chromium against a synthetic issuer. Static UI rules, including responsive and dark styles, use Remix `css(...)` mixins. `src/styles.css` holds font loading, document defaults, theme variables, selection, and reduced-motion rules. Tailwind is not used. Install Chromium once with `npx playwright install chromium` if needed. `npm run dev --workspace @harrhy/auth` starts the UI using an optional app-local `.env`; `docker compose --profile auth up --build auth` starts its opt-in local container at `auth.localhost`. A local UI can render without provider credentials, but real sign-in needs an approved local issuer/client and private mounted credentials.

The synthetic authorization browser script uses four representative applications: 4orm for direct authorization-request login and login CSP, Artbin for return-target login and delegated consent, Ref for archive scopes, and the Rotund portal for silent sessions. Each exercises first-successful login, failed-password retry, and existing-session callback. Client policy tests remain in the Node suite; Radio has its own browser enrollment flow. Maps, Executor, Burger, Lists, Media Admin, Letters to Steve, Radio, Marky, and Navidrome are not each run through the generic browser login lifecycle, so their individual configuration-to-browser-callback combinations are not covered by that matrix. Separate policy, freshness, session, stale-form/restart, and reset checks remain.

Ref's delegated policy separates board and archive permission families. A human
member or admin may request granted `boards-read`/`boards-write` capabilities;
`archive-read`/`archive-restore` remain admin-only. A request cannot mix those
families or request both membership roles. Every requested capability is checked
against the active user grant both before showing consent and when approving it.
`__tests__/ref-delegation.test.mjs` covers these policy boundaries independently
of the generic browser archive-login fixture.

Auth emits one structured `@harrhy/logger` completion per HTTP request, with
an ingress-generated `X-Request-Id`, HTTP method, stable route, response status,
outcome, duration, and build version when known. Delegated policy failures keep
their fixed internal reason codes. When a ZITADEL HTTP rejection reaches the
browser error page, the event also carries the upstream service, fixed phase,
HTTP status, and recognized numeric code, if present. The error page displays
the same request ID as a support reference. This boundary does not log auth URLs,
query parameters, request credentials, provider identifiers or raw errors.
Browser form rejections also record a fixed validator reason. Authorization
redirects distinguish login required, provider session rejected, and client
callback without logging redirect targets or claiming callback delivery.

### DCR scope vocabulary

ZITADEL validates role scopes against the OAuth client's own project before
creating its authorization request. A DCR client can therefore lose a requested
resource permission even when its audience points to the correct resource project.
The DCR project's vocabulary must include both `delegatedRoles` and
`delegatedPermissions` from the reviewed application registry. Defining these keys
permits scope requests; it does not assign a user grant or bypass consent, resource
authorization, or the app's permission-family policy.

[`scripts/configure-dcr.mjs`](scripts/configure-dcr.mjs) is the canonical add-only
recipe. Supply the operator-reviewed effective registry explicitly, including any
approved runtime overlay, the exact native `ZITADEL DCR` project, and an explicit
credential authorized to manage that project's role definitions. There is no
management-reader, bootstrap-key, or host-secret-path fallback. From this workspace:

```sh
node scripts/configure-dcr.mjs \
  --api-origin "$HARRHY_AUTH_API_ORIGIN" \
  --organization-id "$HARRHY_AUTH_ORGANIZATION_ID" \
  --applications-file "$HARRHY_AUTH_APPLICATIONS_FILE" \
  --project-id "$HARRHY_AUTH_DCR_PROJECT_ID" \
  --credential-file "$HARRHY_AUTH_DCR_CREDENTIAL_FILE" \
  --role boards-read --role boards-write
```

The default is a read-only plan. Repeat with `--apply` only after reviewing the
missing keys. `--role` restricts the operation to declared keys; omit it to plan
the complete deduplicated delegated vocabulary. Inventory is paginated, retries
re-read existing definitions, and successful application verifies every prior and
selected key remains present. It never removes roles, creates projects or clients,
changes DCR security mode, or creates user grants. An uncertain write is not
replayed automatically; inspect a new plan before retrying. Already-created
authorization requests retain their processed scopes and must not be mistaken
for proof of the repaired vocabulary.

### Real local sign-in

The opt-in profile in `local-real/` uses pinned ZITADEL 4.20.0 and PostgreSQL 17 images, this Auth UI, and the actual Artbin OAuth callback. It creates one synthetic organization user and an Artbin member grant. Each worktree gets a separate Compose project and database, isolated from production; `@harrhy/dev-auth` remains the faster in-memory fixture for narrow checks. Docker is needed only for the provider and database. Node 26 and the repository dependencies run the two apps on loopback.

```sh
npm run auth:real:init
npm run auth:real:up
npm run auth:real:seed
```

In separate foreground terminals, run `npm run auth:real:ui` and `npm run auth:real:artbin`. Then open <http://localhost:18892/login> or run `npm run auth:real:smoke` for a browser sign-in, native authorization code, Artbin callback, session, and reload check. Stop the app terminals with Ctrl-C and run `npm run auth:real:down` to stop the provider. `down` preserves its local database and credentials for the next start. The generated local sign-in password is in the ignored, mode 0600 `apps/auth/.local-real/seed.json`; bootstrap PAT files are mode 0600 after seeding; do not paste it into issues or logs. The local Auth UI is <http://localhost:18888>, and the native issuer is bound to <http://localhost:18887> only. Ports 18887, 18888, and 18892 must be free before starting. No standard dev command or CI job starts this profile.

The native setup writes only synthetic project/client IDs to local configuration. The operator PAT, login PAT, database password, master key, resource client secret, and local user password stay under ignored `apps/auth/.local-real/`. The committed production client IDs, callback URLs, role names, and issuer URLs in `config/` are public identifiers and policy, not credentials. Production keys, tokens, account records, and SQLite files are never copied into the local profile. The provider and Artbin share no database. `local-real/seed.mjs` checkpoints each native creation; if one fails with an uncertain outcome, it stops instead of creating a duplicate on retry.

The app is independently containerized by `Dockerfile`. The Auth publisher checks this workspace and publishes `ghcr.io/jackharrhy/auth` when Auth or a relevant shared build input changes; it does not select the production container. Production settings, DNS, sealed credential files, both SQLite data files, appearance state, and backups are owned by Infra. Set `PUBLIC_ORIGIN`, `ZITADEL_API_URL`, `ORGANIZATION_ID`, the reviewed client/project IDs, and the relevant read-only credential file paths there. Keep `ACCESS_DB_FILE`, `RADIO_ENROLLMENT_DB_FILE`, `DOODLE_POOL_FILE`, and `AUTH_SUPPORT_CONFIG_FILE` with their existing data and recovery material. An Auth UI restart invalidates in-memory browser and support sessions; durable support cleanup still uses the sealed support key and access database. No source import or container build activates native impersonation.

## Media identity lifecycle (in development)

Services → Service accounts (`/manage/media`) provides administrator-only native inventory, discrepancies, exact-ID mapping review/confirmation and durable review history in the existing access database. Optional private `AUTH_MEDIA_INSTANCES_FILE` configures bounded read-only Jellyfin inventory or timestamped operator snapshots; no configuration means no native scan. `src/connected-accounts.mjs` owns mapping persistence; `account-inventory.mjs`, `jellyfin-inventory.mjs`, and `connected-account-pages.tsx` own readers and views. The [implementation contract](../../docs/auth/media-identities.md) documents source configuration, full-roster permission verification and remaining account/invitation/provisioning layers. Mapping alone never grants access or changes native accounts. `src/media-service-actions.mjs` adds durable reviewed Jellyfin disable and separate Seerr account-and-request removal claims, read-only disable uncertainty recovery and transition audit. The shared access store owns this ledger. Optional private `AUTH_MEDIA_WRITES_FILE` supplies a separate array of `{service, instance, baseUrl, writeTokenFile}` for Jellyfin/Seerr adapters; absent configuration disables all native writes with no roster credential fallback. To enable only reviewed account creation/import, set the separate private `HARRHY_AUTH_MEDIA_PROVISIONING_FILE` to an array with the same entry shape while leaving `AUTH_MEDIA_WRITES_FILE` absent. It configures provisioning adapters only, never disable/removal adapters. When the new setting is absent, existing deployments retain their shared write-file behavior; an explicit empty array disables provisioning even if the lifecycle file is configured. Inventory-only instances show an explanatory disabled creation page without requesting native libraries or the Auth directory. Confirmed non-administrator mappings expose separate native action review forms. Administrator-only `/manage/media/actions` review/confirm/reconcile routes require the original reviewer, fresh live administrator membership, same-origin CSRF and explicit configured write capability; the native target and reviewed policy/request revision are re-read before any write. The media entry page shows only the service picker and a history link. Each service opens a concise, server-filtered users list (`?q=&state=`); exact encoded native-ID detail links open one account, then a separate contextual `/link` or `/action` form before the existing consequence review. All steps are ordinary server-rendered links/forms with reload, deep-link and browser-history support. `/manage/media/history` retains mapping, native-action and creation review receipts; creation/import forms are scoped to the chosen service and instance. HTTPS Chromium fixtures cover Jellyfin disable and Seerr destructive confirmation, forged Origin, typed count mismatch, replay prevention and mobile review layouts against isolated synthetic native APIs. Seerr removal reviews complete bounded request pagination and requires explicit native ID/count confirmation; its API has no conditional delete, so concurrent new requests may also be removed. Failed deletes remain effect-unknown and are never replayed. `src/identity-onboarding.mjs` now backs People → Add person with durable review, separate creation and exact-recipient invitation confirmation, plus proof-bound recipient password setup at `/invitation`. Creation is disabled without an explicit server-only `AUTH_PROVISIONING_TOKEN_FILE`; do not reuse the management reader by assumption. The former immediate initial-password creator is removed. Native invitation delivery requires the configured public origin to be HTTPS. No invitation grants service access. `node apps/auth/__tests__/native-invitation-contract.mjs` is an opt-in synthetic native-provider check after local-real setup. `node apps/auth/__tests__/native-invitation-browser.mjs` additionally validates the actual HTTPS administrator/recipient UI, native SMTP delivery into pinned isolated Mailpit, first-password setup and ordinary native sign-in with no service grants. It needs Docker, OpenSSL and Chromium, uses its own local access database, removes its SMTP configuration on success and never uses production settings. Only the verified installed-provider invalid-invitation error restores a pending invitation after wrong proof; ambiguous proof/password responses remain unknown and cannot be replayed. Actual HTTPS checks cover wrong-proof then correct-proof completion and non-retry rendering for lost creation, invitation, verification and password responses. See the implementation contract for receipt/retry boundaries. Deployment capability is configured independently; source support does not imply that native writes are enabled.

People → person → Set up Jellyfin carries the selected person into a compact username/library/activity-note form. One review shows the person, new username, named libraries and permission consequences; exact IDs, full policy and audit metadata stay in a closed Technical details disclosure. The separate Jellyfin password is submitted only at final HTTPS confirmation. Newly reviewed Jellyfin operations explicitly authorize **Create and link account** using versioned `create-and-link-v1` intent. `src/media-provisioning.ts` durably checkpoints native success as `link-pending` before linking only the exact returned ID. The connected-account insert, linked receipt state and transition event commit in one SQLite transaction. A failed local link leaves an honest created-but-not-linked receipt with Finish linking account: this rechecks the active exact Auth identity and exact native account/policy read-only, never creates an account or sets a password again. Unknown native effects stay stopped. Legacy pending/created reviews have no combined approval and never gain automatic linking; no existing production account is backfilled. Mapping alone grants neither service eligibility nor SSO. Same-actor claims, fresh administrator/CSRF checks and five-minute creation review remain enforced. Passwords are never persisted. `src/jellyfin-provisioning.ts` reviews explicit libraries and applies a new-account-only playback profile before setting a separate native password. `node apps/auth/__tests__/jellyfin-provisioning-native.mjs` is an opt-in Docker check against the pinned installed Jellyfin 12.4 image, using disposable tmpfs state and a random loopback port, never production configuration. It proves real creation, policy verification, recipient sign-in, compact-ID inventory and synthetic disable. HTTPS synthetic Chromium coverage includes the actual creation routes, policy/password ordering, forged Origin rejection, replay protection and 390/768/1440px reviews. The same page also offers separate Seerr exact-ID import from a confirmed Jellyfin mapping: it prevalidates the exact native ID through Seerr’s configured Jellyfin server, rejects existing Seerr associations, reviews permission 160 (REQUEST + AUTO_APPROVE), checkpoints the returned Seerr ID and verifies its type/native association/permissions. Global-default races become effect-unknown, never automatic repair/deletion. Import creates no requests or automatic mapping. Synthetic Chromium covers combined Jellyfin creation/linking and reviewed one-ID Seerr import without a password or grants. `node apps/auth/__tests__/seerr-provisioning-native.mjs` proves this flow against pinned installed Seerr 3.5.2 and Jellyfin 12.4 images on a disposable unique Docker network, with tmpfs state and random loopback ports: real new-user import, returned-ID receipt, permission 160, native recipient sign-in and duplicate-association rejection. It reads no host configuration or production data and removes only its own containers/network. Installed Seerr API keys are base64; the write transport accepts that native format without allowing header controls. The new combined UX requires owner PR review before merge or deployment; source support is not a rollout or production-account migration.

## Synthetic UI review

For an interactive review of the actual management routes, run `node __tests__/fixtures/management-preview.mjs --origin https://YOUR-PRIVATE-PREVIEW-HOST --port 19067 --minutes 55` from `apps/auth`. Supply the registered private HTTPS origin explicitly; there is no owner-specific hostname in the fixture or normal tests. The shared `management-server.mjs` binds only loopback, uses an ephemeral port by default, and starts Auth with explicit disposable provider/native configuration rather than inherited host settings. The separate preview entry point accepts a bounded 1–720 minute review window and explicitly refreshes inventory each minute from the current synthetic native state, including created/disabled/deleted accounts. Ordinary browser fixtures do not auto-refresh, preserving stale-snapshot coverage. Register the selected port/origin through the existing private Infra preview registry separately and bound a detached backend independently. Sign in as `operator` with the synthetic password `fixture-password`. Stopping the fixture removes its scratch database and credentials. Standard Chromium checks use this same isolated fixture with a fresh local HTTPS origin, never the private preview network.

`PORT=18809 node apps/auth/__tests__/fixtures/ui-preview.mjs` (from the repository root) serves a loopback-only, GET-only background explorer (`/login`) and authenticated-header (`/`) fixture. It imports the UI without starting Auth, loading credentials, or connecting to a provider/database; the interior identity is explicitly synthetic. Do not use it as an authenticated app or production runtime. Login submissions are disabled. `__tests__/browser/ui-polish.mjs` checks responsive centering/header, explorer controls, deterministic screenshots across reload, reduced motion, and unavailable/context-lost WebGL fallback. It runs in `test:browser`.

The fixture defaults to animated Silk braid WebGL with a whole-background fade. Background options switch immediately between plain paper and WebGL, with three existing effects and three palette choices. Every change updates the shareable URL without submitting or reloading. Fixed dates/seeds and time-zero rendering hold a stable choice for critique. Optional animation respects reduced motion by freezing WebGL; unavailable/context-lost WebGL leaves plain paper. There is no SVG artwork, SVG combination, or SVG fallback in this explorer. Optional entrance fades the selected background layer as a whole. These controls and modules exist only under `__tests__/fixtures`; the product motion module is not loaded by the explorer. The production login uses the approved Silk braid default, automatic motion and whole-background fade, without these fixture controls. Persisted non-waves gallery choices/tuning remain honored; legacy waves entries are filtered in memory, not rewritten.

The removed Waves choice drew heavier lines every sixth band; it was not a separate bars overlay. Its legacy shader branch is not an offered effect. The former paper control only changed the CSS beneath the opaque shader paper (and was overridden in dark mode), so its small indirect difference was misleading; the control was removed. Color choices tune the existing shader palette instead.

## Routing migration boundary

Sign-in, delegated consent, account, email recovery, enrollment, device approval, the app directory, sessions, access management, People, groups, and service inventory now render through Remix 3 and use `@harrhy/ui` controls. All browser pages now render with Remix 3 components, including support and failure states. Public assets, health, enrollment completion, issuer policy, and support JSON endpoints now use Remix Web Request/Response routers. Browser requests now enter through a Remix Web Request/Response router. Login, logout, enrollment, account details, email verification and recovery, password, authorization, device, app directory, management, and support actions now enter through explicit Remix routes. Shared session, CSRF, and provider-session checks still live in the browser boundary while the route controllers own their actions. The shell, login layout, shared controls, directory cards, list rows, and responsive styling use Remix `css(...)` mixins; the small plain stylesheet holds document-level rules and font loading. ZITADEL and its state remain separate. `@harrhy/identity` stays a consumer validation/client package.
