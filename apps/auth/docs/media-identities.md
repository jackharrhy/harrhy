# Reviewed media identity lifecycle

This feature is in development, not deployed. Services → Media identities (`/manage/media`) exposes read-only native inventory and reviewed exact-ID linking for active Auth administrators. `src/media-identities.mjs` owns mappings and audit reviews in the existing access SQLite database; `media-inventory.mjs` and `jellyfin-inventory.mjs` own bounded read-only sources. Mapping does not change directory eligibility, issuer provisioning or native permissions.

## Boundaries

An issuer subject, a portal assignment, a native account and a native session are different resources. The existing access model's `links` authorize reviewed project-role assignment; media identity mappings do not replace or modify those guards. In particular, Jellyfin and Seerr sharing directory eligibility does not establish that both native accounts are linked.

Mappings use exact `(issuer, subject)` and `(service, instance, nativeId)` tuples. Names and email are display data, not matching keys. A native account and a subject each have at most one mapping per service instance. A mapping records operator, reason and time; it grants no role, changes no native account and authorizes no login. No automatic account deletion, reassignment or reconciliation is supported.

The ledger accepts a host-owned SQLite connection. Its callers must enforce active Auth administrator membership, CSRF/Origin validation and verified organization-scoped issuer inventory. The module is not an authorization boundary exposed directly to users. Review and confirmation must each obtain read-only native inventory; unavailable/stale inventory cannot prove account absence. Reviews expire after five minutes and require the same operator, exact current active issuer subject and unchanged native account. SQL uniqueness and transactional confirmation prevent two conflicting reviews from silently replacing each other. Completed confirmation is idempotent.

## Installed Jellyfin disable contract (not runtime-enabled)

Infra's installed 12.4 OpenAPI confirms exact-user `GET /Users/{userId}` and full-policy `POST /Users/{userId}/Policy`; the latter is not a partial patch. `src/jellyfin-lifecycle.mjs` now provides a bounded, separate-write-credential adapter for reviewed non-administrator disable. It rereads the exact native ID and compares the entire reviewed policy before mutation, requires the caller's durable effect claim before POST, preserves every policy field except `IsDisabled`, and verifies the complete policy after writing. Transport failure or verification drift returns `effect-unknown`, never a retry or success. Already-disabled accounts need no write. No delete, password change, login, token or session endpoint is called.

The shared access store now owns the action ledger. Optional host-only `AUTH_MEDIA_WRITES_FILE` configures a separate array of `{service, instance, baseUrl, writeTokenFile}`; only Jellyfin and Seerr are supported, duplicate instances are rejected, and no inventory credential fallback exists. Absent configuration disables native writes. Browser routes/UI are not connected yet; configuration alone exposes no mutation endpoint. `src/media-service-actions.mjs` now owns durable disable review, effect claims, recovery and append-only transition audit on the host SQLite connection. It requires a confirmed exact-ID mapping, the same operator and a five-minute review. Claims serialize overlapping native-account writes before the adapter can mutate. A crash leaves `effect-unknown`; recovery only reads the exact account and accepts the entire reviewed disabled policy, never retries a write or asserts session revocation. A claimed account cannot be submitted through another review to bypass uncertainty. The host must still supply administrator/CSRF boundaries and explicitly approved instance-specific write authority when wiring the UI; this module alone enables no runtime action. Its synthetic tests prove policy preservation, drift rejection, claim-before-write and unknown effects; they do not prove installed-server behavior or credential authority. The installed API evidence establishes neither per-user all-token revocation nor all-session termination. Disable therefore always retains `sessionRevocation: manual-required`; it cannot authorize issuer deletion. The installed Seerr source review below establishes why permission zero or deletion is not an offboarding substitute.

## Installed Seerr contract (not runtime-enabled)

Infra supplied a narrow source-only extract from the installed Seerr 3.5.2 image, with exact image provenance retained privately alongside the extract. No roster, configuration, credentials or application data were read for this review. The relevant installed files are `dist/routes/user/index.js`, `dist/routes/auth.js`, `dist/middleware/auth.js`, `dist/lib/permissions.js` and `dist/entity/{User,Session}.js`. This establishes source behavior, not deployment credential authority or a successful runtime experiment.

- User creation (`POST /user`, relative to the API mount) requires `MANAGE_USERS`, checks email uniqueness and creates a local user with the server's global `defaultPermissions`. An explicit password is hashed; otherwise email notifications must be enabled and a generated password is emailed. Neither branch is an Auth invitation or a reviewed per-person least-privilege policy. Do not invoke it as part of issuer invitation delivery.
- Jellyfin import (`POST /user/import-from-jellyfin`) consumes `jellyfinUserIds`, enumerates Jellyfin users through the configured server credential, normalizes IDs and skips already-imported IDs. New users inherit global `defaultPermissions`. It is not a supported per-person permission selection or an automatic matching authorization. The loop does not explicitly reject a requested ID missing from the enumerated map before constructing a user, so callers must not treat submitted IDs as provider-validated proof.
- Single-user update (`PUT /user/:id`) assigns `username` and `permissions`, with owner/administrator safeguards. It provides no disabled field or lifecycle transition. Preserve existing request permissions `160`; no permission rewrite is enabled here.
- Permission zero does not disable authentication. `hasPermission(0, value)` returns true; session middleware reloads any extant session user without a disabled check; local sign-in validates email/password and establishes a session without checking permissions. Removing request permissions cannot honestly be reported as account disable or session revocation.
- User deletion explicitly loads the exact user with their requests, removes those request records through the repository in chunks, then deletes the user. This is the expected destructive account-and-request cleanup capability, distinct from non-destructive offboarding or revocation. Follow-up review of `MediaRequestSubscriber.afterRemove → handleRemoveParentUpdate` establishes database parent-media/season status maintenance, not downloaded-file cleanup. It retains available/partially-available media status and may reset other statuses to unknown/deleted based on remaining requests; a database `DELETED` status is not a filesystem deletion. `SeasonRequest.request` has database `ON DELETE CASCADE`. The media subscriber can mark related requests completed; its request-update Arr calls require approved status, not completed status. No Arr removal, download-client removal or filesystem deletion call was found on this reviewed removal path. Do not promise downloaded-media deletion or add it implicitly. These are source findings, not a live destructive experiment.
- Logout destroys the caller's session; the reviewed source does not establish an administrative exact-user all-session/token revocation API. The session entity stores opaque session JSON, not an exposed supported revocation contract. Direct database edits are not an adapter.

Seerr non-destructive disable and all-session revocation therefore remain `manual-required`. Intentional account-and-request deletion must instead have its own exact-native-ID review, request count/impact where available, explicit destructive confirmation, same-actor fresh revision, administrator/capability and CSRF checks, and durable claim-before-effect/uncertainty handling. Never automatically delete unknown or native-only accounts, infer Auth identity deletion, or broaden cleanup into Arr, qBittorrent or filesystem actions. `src/seerr-lifecycle.mjs` now implements the isolated removal adapter: exact positive numeric ID (never owner ID 1), non-administrator target, complete bounded request pagination (at most 10,000 records), a minimal request ID/status/update-time impact summary, exact review reinspection and durable claim before DELETE. It never stores full user/request payloads. The ledger requires the explicit `remove-account-and-requests` operation and typed exact-ID/request-count confirmation; disable remains separate. There is no native conditional delete: requests arriving between reinspection and deletion may also be removed, which the UI must disclose. A failed delete may be partial and stays effect-unknown, with no write retry or automatic recovery. The administrator browser routes now expose these as distinct explicit operations only for confirmed non-administrator mappings, with same-actor reviews, fresh active administrator verification on each POST, same-origin CSRF, configured write capability and five-minute review expiry. `/manage/media` links the original reviewer’s recent durable action records. HTTPS Chromium verifies native disable, intentional Seerr removal, exact typed count rejection, Origin denial, one-time effect claims and responsive review forms against synthetic native APIs. No live operation has been performed. Provisioning must still establish an explicit least-privilege policy and safe uncertainty/reconciliation semantics before an adapter can be offered in the UI. Existing production native identities, passwords and requests remain unchanged; household native-only cases are not mutation test targets.

## Read-only inventory configuration

Infra owns production configuration and credentials. `AUTH_MEDIA_INSTANCES_FILE` optionally points to a private JSON array; absent configuration yields an honest unconfigured screen, never a production scan. Instance names/keys are explicit and stable. The browser cannot supply endpoints or credential paths.

A server-side Jellyfin reader entry:

```json
[
  {
    "service": "jellyfin",
    "instance": "reviewed-server",
    "name": "Jellyfin",
    "adapter": "jellyfin",
    "baseUrl": "http://127.0.0.1:8096",
    "tokenFile": "/run/secrets/jellyfin-inventory-token",
    "fullRosterReviewed": false
  }
]
```

Keep `fullRosterReviewed` false until Infra proves that the selected credential can enumerate the full unfiltered roster on the installed server. False fails unavailable without reading credentials or making a request. A server API key is privileged; this is **not** a claim that Jellyfin has endpoint-scoped/read-only keys. This adapter only issues `GET /Users`, with no filters, no redirects, a five-second timeout and a 1 MiB response cap. It uses server-side `Authorization: MediaBrowser Token="…"`, accepts validated PascalCase/CamelCase `UserDto` fields, and treats null/missing policy, partial/wrapped results and duplicate IDs as unavailable. Installed OpenAPI evidence supplied by Infra describes `/Users` as a top-level array, with no pagination contract and only `isHidden`/`isDisabled` filters. Do not filter or truncate an authoritative inventory. No credential reaches rendered data or audit bodies.

Alternatively configure a source with `service`, `instance`, `name`, and absolute `snapshotFile` (no `adapter`). The file contains `{service, instance, state: "available", observedAt, accounts}`. Each account has only `nativeId`, `name`, boolean `disabled` and boolean `administrator`. Source scope must match configuration. Readers strip extra fields, reject duplicate IDs/oversized files, and retain the source timestamp; five-minute-old/future/invalid snapshots do not permit linking. An unavailable source is not an empty roster. Operator-written snapshots should use atomic replacement and least-privilege file permissions. Neither source writes to a native service.

No production instance configuration or credential is committed. Local browser fixtures use temporary synthetic files, subjects and native IDs.
